**Target Architecture:** ARM Cortex-M0+ (PY32F071xB) @ 48 MHz  
**Flash Ceiling:** 120,832 bytes (118.0 KB) | **Long-Term Target:** ≤ 80 KB (< 65% utilization)  
**Status:** Living Engineering Blueprint for Multi-Agent Execution

---

## 1. Executive Summary & Architectural Motivation

Kern is a high-assurance, `#![no_std]`, zero-heap amateur radio microkernel engineered for ARM Cortex-M0+ silicon. While functional completeness has been achieved across radio modulation, RigWire RPC, KernFS storage (ORDS-01), KRX relocatable execution, and graphical compositing, the firmware currently occupies **118,968 bytes of Flash (98.5%)**.

This tight utilization leaves insufficient headroom for installable third-party userland applications, extended amateur radio digital modes, or expanded filesystem partitions.

Crucially, this consumption is **not caused by feature count**. Rather, deep static analysis of the compiled binary (`arm-none-eabi-nm`) reveals systemic architectural overengineering:
1. **Proliferation of Monolithic C-ABI Shims:** 183 separate `extern "C"` syscall functions in `firmware::runtime::syscall` consuming **12,717 bytes**, many inlining full graphical algorithms (`api_draw_line`, `api_fill_rect_dither`, `api_scroll`, `api_ui_draw_menu_item`).
2. **Excessive rodata Pointer Tables in Declarative Apps:** `apps::settings` consumes **7,795 bytes**, driven by dozens of `&[&'static str]` option slice tables where every string pointer and slice descriptor costs 8–16 bytes on 32-bit ARM.
3. **Mega-Function Inlining under ARMv6-M Register Starvation:** Monolithic handlers like `dispatch_wire_record` (4.6 KB) and `dispatch_event` (2.2 KB) inline multi-layer branches, exhausting the 8 low registers (`r0`–`r7`) and generating massive stack frame push/pop sequences.
4. **Duplicated Binary Format Inspection:** Package validation and header parsing are duplicated across `catalog::inspect_package` (556 B), `loader::launch_krx_package` (1,416 B), and `native_runner::load_native_from_storage` (1,508 B).
5. **Procedural Math & Duplicated Widget Layouts:** Widgets duplicate integer-to-string routines, coordinate clamping, and layout math that could be computed via compact table strides.

## 2. Silicon Constraints & The Five Fallacies of Flash Optimization

Why do naive flash savings projections (e.g. "~1,300 B from RadioCoordinator de-monomorphization", "~5,500 B from syscall thinning") repeatedly fail to materialize upon empirical verification? Deep static analysis across the ARMv6-M binary reveals five fundamental fallacies:

### Fallacy 1: The Monomorphization Fallacy (1 Concrete Type = 0 Duplication)
- **The Myth:** "Generics cause code bloat! De-monomorphizing generic functions (`<R: RadioService>`) will save thousands of bytes."
- **The Empirical Reality:** Monomorphization only duplicates code if a generic function is called with **two or more distinct types** (`foo<TypeA>` and `foo<TypeB>`).
- In Kern's hardware abstraction layer, traits like `RadioService`, `StorageService`, and `AudioService` represent physical silicon. There is only **one** radio chip (`Bk4829`), **one** flash chip (`Py25q16`), and **one** context (`SysContext`).
- Static ELF symbol inspection proves:
  - `<RadioCoordinator>::tick_10ms::<Bk4829>` has **exactly 1 instantiation** (1,876 B).
  - `<RadioCoordinator>::start_tx::<Bk4829>` has **exactly 1 instantiation** (244 B).
  - `<RadioCoordinator>::request_ptt_start::<Bk4829>` has **exactly 1 instantiation** (232 B).
  - `<RadioCoordinator>::stop_tx::<Bk4829>` has **exactly 1 instantiation** (212 B).
- Because only ONE copy was ever generated by LLVM, replacing `fn tick_10ms<R: RadioService>(&mut self, radio: &mut R)` with `fn tick_10ms(&mut self, radio: &mut Bk4829)` saves **strictly 0 bytes of Flash**.

### Fallacy 2: The De-Inlining Fallacy (Single Call Site Overhead)
- **The Myth:** "Function X is 4 KB in `nm`! Extracting its branches into `#[inline(never)]` helper functions will shrink the binary."
- **The Empirical Reality:** On ARMv6-M Cortex-M0+, every non-inlined function incurs:
  1. A function prologue (`push {r4..r7, lr}` = 4 to 8 bytes).
  2. A function epilogue (`pop {r4..r7, pc}` = 4 to 8 bytes).
  3. Argument preparation at the caller (`mov r0..r3` = 4 to 12 bytes).
  4. Call branch (`bl` = 4 bytes).
- When a function is called from **only one site**, inlining eliminates all of this overhead and allows LLVM to reuse register allocations across blocks. Marking a single-call-site private helper `#[inline(never)]` **always increases binary size**. (Empirically verified: de-inlining `handle_control_service` increased binary size by **+136 bytes**).

### Fallacy 3: The Data-to-Code Tradeoff (Tables vs Match Trees)
- **The Myth:** "Deleting a 300-byte `.rodata` table will save 300 bytes of Flash."
- **The Empirical Reality:** Flash stores both `.text` (machine instructions) and `.rodata` (constants). If a 304-byte table (`PAGE_METAS`) is replaced by a `match` expression that returns fat pointers (`(&str, &[SettingDef])`), LLVM generates 19 branch targets loading 4 words each (76 words = 304 bytes of immediate loads and jumps). The resulting code instructions exceeded the original table (+48 bytes net penalty).
- *Rule:* Only decompose tables when the accessor can return scalar pointers (1 word) or compact discriminants, avoiding multi-register return overhead.

### Fallacy 4: The C-ABI Fixed Overhead Floor
- **The Myth:** "We can trim 5,500 bytes from `runtime::syscall` by making handlers thinner."
- **The Empirical Reality:** `firmware::runtime::syscall` exports 183 separate `extern "C"` functions. On ARMv6-M, an `extern "C"` function that merely forwards arguments has a physical floor of 16 to 24 bytes (prologue, forwarding, call, epilogue).
- $183 \times 16 \text{ bytes} = 2,928 \text{ bytes}$ of irreducible entry/exit glue.
- Individual function thinning yields diminishing returns. Real savings require **reducing the symbol count** through consolidated dispatchers (e.g. single opcode TVF or vector dispatch).

### Fallacy 5: Stream Cursor Abstraction Tax
- **The Myth:** "A structured `WireBuf` writer with helper methods is more idiomatic and smaller than raw slice copies."
- **The Empirical Reality:** Constant-range slice writes (`out[0..2].copy_from_slice(&val.to_le_bytes())`) are optimized by LLVM directly into 1-cycle `strh`/`str` instructions with **zero runtime bounds checks**. A dynamic cursor introduces offset state tracking, mutable pointer register maintenance, and runtime length comparisons (+392 bytes penalty).

### Architectural Contrast: Kern vs. Inspo Reference Architectures (Falcon, F4HWN, DeltaFW)

| Architectural Attribute | Reference Firmwares (Falcon / F4HWN / DeltaFW) | Kern Microkernel Firmware |
|---|---|---|
| **Resident Footprint** | **~50–60 KB** Flash | **118.5 KB** Flash |
| **Execution Model** | Monolithic super-loop scheduler (`scheduler.c`) | Preemptive capability-based microkernel with IPC |
| **Userland Applications** | **100% External OpenApps (`.app`)** stored on SPI Flash | Dual: Built-in applications + KRX dynamic runtime |
| **Application Invocation** | 4 KiB transient overlay RAM; passes single `app_api_t*` | Fixed-window cache, P0 leaf overlays, shadow stacks |
| **Syscall Layer** | Single flat vtable (`app_api_t`, ~70 function pointers) | 13 separate VTables, 183 C-ABI functions, GOT binder |
| **Settings System** | Flat 2-level array menu (~4–6 KB) | 18-page hierarchical menu engine (~7.5 KB) |
| **Boot Subsystem** | Direct hardware init (~1.5 KB) | Multi-stage animations, recovery screen, provisioning (7.2 KB) |
| **RPC & Remote Control** | Minimal UART command parser (~1.2 KB) | Full RigWire Resource Handle RPC + Chunked File Transfer (4.9 KB) |

### The Core Architectural Dilemma
Kern currently embeds **both** a desktop-class microkernel runtime (virtual memory caching, shadow stacks, capability security tokens, RigWire RPC) **and** a heavyweight built-in application suite (18-page Settings, 7 boot splash modes, graphical recovery screen, embedded provisioning binaries).

To achieve the theoretical limit of 118 KB and reach the long-term target of **≤ 80 KB**, the architecture must shift from *resident monolithic applications* to *microkernel service hosting*, moving non-critical features into external KRX bundles.

## 3. Subsystem Architectural Blueprints

### Phase 1: Syscall Layer Consolidation & Inlined Primitive Extraction
**Location:** `src/firmware/src/runtime/syscall/`  
**Current Footprint:** 4,319 bytes text | **Target:** ~3,000 bytes | **Savings:** ~1,300 bytes

#### Architectural Flaw & Invariant Insight
`firmware::runtime::syscall` defines 183 separate `extern "C"` functions. While originally thought to suffer from monomorphization, syscalls are strictly non-generic C-ABI exports. The real flash cost is the irreducible **16-to-24 byte entry/exit sequence** per function ($183 \times 16 \text{ B} \approx 2.9 \text{ KB}$ floor) plus several functions that inlined full algorithms (`api_draw_line` at 356 B, `api_scroll` at 348 B, `api_fill_rect_dither` at 332 B).

#### Implementation Directives
1. **Unified Canvas Extraction:**
   - Eliminate duplicated drawing algorithms inside `api_draw_line`, `api_fill_rect_dither`, and `api_scroll` by delegating directly to shared, non-inlined `gfx::draw` / `Canvas` routines.
   - Replace manual battery icon drawing in `api_ui_draw_battery` (178 B) with shared delegation to `status_bar::draw_battery`.
2. **Consolidate Low-Traffic Syscalls:**
   - Consolidate fine-grained 1-line getter/setter syscalls into unified query/control entry points, reducing the total count of exported symbols.

---

### Phase 2: Settings Schema Compaction & Decomposed Page Lookups
**Location:** `src/firmware/src/apps/settings/`  
**Current Footprint:** 7,460 bytes | **Target:** ~4,200 bytes | **Savings:** ~3,200 bytes

#### Completed Refactoring (Batch 4)
- **Eliminated `PAGE_METAS` Array:** Deleted the 304-byte static array of 16-byte structs (`PageMeta { title: &str, defs: &[SettingDef] }`).
- **Decomposed Lookups:** Replaced the fat tuple return `get_page() -> (&str, &[SettingDef])` (which forced 4-word return register spilling and 360B of match branch loads) with two independent single-responsibility functions:
  ```rust
  pub fn page_title(page: PageId) -> &'static str { ... }
  pub fn page_defs(page: PageId) -> &'static [SettingDef] { ... }
  ```
  This immediately reduced binary size by **108 bytes Flash** (328 bytes text reduction), with `page_title` compiling to only 28 bytes and `page_defs` to 48 bytes.

#### Remaining Implementation Directives
1. **Packed Null-Delimited Option Strings (`\0` Encoding):**
   - Pack remaining multi-element option lists into single compact string literals (`pub static SHADING_OPTS: &str = "Outline\0Dither\0Solid\0";`).
   - Use `SheetOptions::Packed(str)` to avoid slice-of-pointers relocation tables.

### Phase 4: RigWire Facet Dispatch Flattening & Zero-Copy Payloads
**Location:** `src/firmware/src/services/wire.rs`  
**Current Footprint:** 4,974 bytes | **Target:** ~3,500 bytes | **Savings:** ~1,400 bytes

#### Architectural Flaw & Invariant Insight
Initial experiments with a dynamic stream cursor (`WireBuf` with write pointers and per-byte bounds checks) **increased binary size by +392 bytes** on ARMv6-M due to pointer tracking and branch checks. On Cortex-M0+, constant-range slice copies (`out[0..2].copy_from_slice(&val.to_le_bytes())`) lower directly to 1-cycle `strh`/`str` instructions with zero overhead.

#### Implementation Directives
1. **Zero-Copy Payload Borrowing:**
   - In `dispatch_wire_record`, eliminate the redundant 128-byte stack buffer `let mut payload_buf = [0u8; 128];`.
   - Borrow payload slices directly from the transport driver buffer `hw.wire.current_payload(header)` to eliminate stack copying and reduce register exhaustion in `dispatch_wire_record`.
2. **Consolidate Response Status Dispatch:**
   - Factor common status code return envelopes (`send_status(hw, header, status)`) into an `#[inline(never)]` common tail to eliminate duplicate framing sequences.

### Phase 6: RadioCoordinator State Machine Control & Squelch Inlining
**Location:** `src/firmware/src/services/radio/coordinator.rs`  
**Current Footprint:** 3,420 bytes (`tick_10ms` alone is 1,876 bytes) | **Target:** ~2,600 bytes | **Savings:** ~800 bytes

#### Architectural Flaw & Invariant Insight
Initial planning assumed `RadioCoordinator` suffered from generic monomorphization bloat. Static ELF inspection disproved this: every generic method in `RadioCoordinator` has **exactly one concrete instantiation** (`<Bk4829>`), meaning syntax de-monomorphization yields 0 bytes of Flash savings.

The real driver of the 1,876-byte `tick_10ms` footprint is **deep inlining of independent state machines**: `tick_tx` (TX power ramp, audio mute), `tick_tone_burst` (1750 Hz tone timeout), `tick_arbitrator` (priority lock countdown), `process_carrier_active` (CTCSS/DCS decode, sub-audible reverse burst, tail muting), `adaptive_squelch` update, and `dual_watch_tick`.

#### Implementation Directives
1. **Separate Infrequent Exception Paths:**
   - Mark error and timeout handlers (`notify_fsk_error`, `request_ptt_stop`, `ste.reset()`) as `#[inline(never)]`.
2. **Decompose Carrier Active Processing:**
   - Factor `process_carrier_active` and CTCSS reverse-burst detection into dedicated non-inlined subroutines called across both VFO channels.

### Phase 7: Boot Splash & System Recovery De-duplication
**Location:** `src/firmware/src/boot/orchestration.rs`, `src/firmware/src/boot/recovery.rs`  
**Current Footprint:** 7,203 bytes (`run_boot_splash` 1,616 B, `draw_recovery_screen` 984 B) | **Target:** ~4,200 bytes | **Savings:** ~3,000 bytes

#### Architectural Flaw
`run_boot_splash` duplicates frame interpolation math, canvas blitting, and key polling. `draw_recovery_screen` manually formats hex lines, stack markers, and boxes using independent procedural code.

#### Implementation Directives
1. **Consolidated Boot Dialog Renderer:**
   - Share the box, banner, and key-prompt renderer (`render_dialog`) across boot stages, recovery, and format prompts.
2. **Compact Splash Key Polling:**
   - Factor splash animation ticking and key break detection into a unified, tight event poll.

### Phase 8: OpenApps / KRX Overlay Runtime Unification (from Falcon / F4HWN)
**Location:** `src/firmware/src/runtime/native_runner.rs`, `src/kernel/src/proc/krx.rs`  
**Current Footprint:** ~18,000 bytes combined | **Target:** ~12,000 bytes | **Savings:** ~6,000 bytes

#### Inspiration from Falcon & F4HWN Architecture
Analysis of Falcon (`inspo/Falcon-firmware-UV-K1-K5v3/`) and F4HWN reveals how community firmwares run dozens of full-featured apps (APRS, CW Keyer, SSTV, AIS, Spectrum) within 118 KB Flash:
1. **Transient Arena as Overlay RAM:**
   - All external applications run inside the 4 KiB sector cache / transient arena (`TRANSIENT_ARENA`).
   - The resident firmware only maintains the kernel, the hardware drivers, and the compositor.
2. **Zero-Copy ABI Table:**
   - Resident services are exposed via clean static function tables (`KrxApiTable` / `app_api_t`), eliminating dynamic dispatch overhead in userland.
3. **De-duplicate Relocation Routines:**
   - Consolidate delta relocation application in `native_runner::apply_package_relocs` to standard pointer-offset arithmetic, ensuring P0 leaf overlays and resident apps share identical execution trampolines.

## 4. Execution Protocol & Verification Standard

Successor agents must execute this master plan in structured, atomic batches:
1. **Zero-Warning Policy:** Run `./kern check` before and after every modification. Zero compiler warnings tolerated.
2. **Target Memory Verification:** Run `./kern size` to measure exact byte deltas. Verify that:
   - Flash size decreases monotonically.
   - SRAM utilization remains ≤ 12.3 KB (≤ 75%).
3. **Automated Test Suite:** Run `cargo test --target x86_64-unknown-linux-gnu -p kernel -p kernfs -p utils` to prevent semantic regressions.
4. **Git Staging Rules:**
   - Commit only workspace changes: `git add -u src/ docs/`.
   - **STRICTLY NEVER** stage or commit files in `inspo/*`.
