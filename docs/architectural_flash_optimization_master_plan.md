## 1. Executive Summary & Architectural Motivation

Kern is a high-assurance, `#![no_std]`, zero-heap amateur radio microkernel engineered for ARM Cortex-M0+ silicon. While functional completeness has been achieved across radio modulation, RigWire RPC, KernFS storage (ORDS-01), KRX relocatable execution, and graphical compositing, the firmware currently occupies **118,968 bytes of Flash (98.5%)**.

This tight utilization leaves insufficient headroom for installable third-party userland applications, extended amateur radio digital modes, or expanded filesystem partitions.

Crucially, this consumption is **not caused by feature count**. Rather, deep static analysis of the compiled binary (`arm-none-eabi-nm`) reveals systemic architectural overengineering:
1. **Proliferation of Monolithic C-ABI Shims:** 183 separate `extern "C"` syscall functions in `firmware::runtime::syscall` consuming **12,717 bytes**, many inlining full graphical algorithms (`api_draw_line`, `api_fill_rect_dither`, `api_scroll`, `api_ui_draw_menu_item`).
2. **Excessive rodata Pointer Tables in Declarative Apps:** `apps::settings` consumes **7,795 bytes**, driven by dozens of `&[&'static str]` option slice tables where every string pointer and slice descriptor costs 8–16 bytes on 32-bit ARM.
3. **Mega-Function Inlining under ARMv6-M Register Starvation:** Monolithic handlers like `dispatch_wire_record` (4.6 KB) and `dispatch_event` (2.2 KB) inline multi-layer branches, exhausting the 8 low registers (`r0`–`r7`) and generating massive stack frame push/pop sequences.
4. **Duplicated Binary Format Inspection:** Package validation and header parsing are duplicated across `catalog::inspect_package` (556 B), `loader::launch_krx_package` (1,416 B), and `native_runner::load_native_from_storage` (1,508 B).
5. **Procedural Math & Duplicated Widget Layouts:** Widgets duplicate integer-to-string routines, coordinate clamping, and layout math that could be computed via compact table strides.

## 2. Silicon Constraints & The Five Fallacies of Flash Optimization

Why do naive flash savings projections (e.g. "~1,300 B from RadioCoordinator de-monomorphization", "~5,500 B from syscall thinning") repeatedly fail to materialize upon empirical verification? Deep static analysis across the ARMv6-M binary reveals five fundamental fallacies:

### Fallacy 1: The Monomorphization Fallacy (1 Concrete Type = 0 Duplication)
- **The Myth:** "Generics cause code bloat! De-monomorphizing generic functions (`<R: RadioService>`) will save thousands of bytes."
- **The Empirical Reality:** Monomorphization only duplicates code if a generic function is called with **two or more distinct types** (`foo<TypeA>` and `foo<TypeB>`).
- In Kern's hardware abstraction layer, traits like `RadioService`, `StorageService`, and `AudioService` represent physical silicon. There is only **one** radio chip (`Bk4829`), **one** flash chip (`Py25q16`), and **one** context (`SysContext`).
- Static ELF symbol inspection proves:
  - `<RadioCoordinator>::tick_10ms::<Bk4829>` has **exactly 1 instantiation** (1,876 B).
  - `<RadioCoordinator>::start_tx::<Bk4829>` has **exactly 1 instantiation** (244 B).
  - `<RadioCoordinator>::request_ptt_start::<Bk4829>` has **exactly 1 instantiation** (232 B).
  - `<RadioCoordinator>::stop_tx::<Bk4829>` has **exactly 1 instantiation** (212 B).
- Because only ONE copy was ever generated by LLVM, replacing `fn tick_10ms<R: RadioService>(&mut self, radio: &mut R)` with `fn tick_10ms(&mut self, radio: &mut Bk4829)` saves **strictly 0 bytes of Flash**.

### Fallacy 2: The De-Inlining Fallacy (Single Call Site Overhead)
- **The Myth:** "Function X is 4 KB in `nm`! Extracting its branches into `#[inline(never)]` helper functions will shrink the binary."
- **The Empirical Reality:** On ARMv6-M Cortex-M0+, every non-inlined function incurs:
  1. A function prologue (`push {r4..r7, lr}` = 4 to 8 bytes).
  2. A function epilogue (`pop {r4..r7, pc}` = 4 to 8 bytes).
  3. Argument preparation at the caller (`mov r0..r3` = 4 to 12 bytes).
  4. Call branch (`bl` = 4 bytes).
- When a function is called from **only one site**, inlining eliminates all of this overhead and allows LLVM to reuse register allocations across blocks. Marking a single-call-site private helper `#[inline(never)]` **always increases binary size**. (Empirically verified: de-inlining `handle_control_service` increased binary size by **+136 bytes**).

### Fallacy 3: The Data-to-Code Tradeoff (Tables vs Match Trees)
- **The Myth:** "Deleting a 300-byte `.rodata` table will save 300 bytes of Flash."
- **The Empirical Reality:** Flash stores both `.text` (machine instructions) and `.rodata` (constants). If a 304-byte table (`PAGE_METAS`) is replaced by a `match` expression that returns fat pointers (`(&str, &[SettingDef])`), LLVM generates 19 branch targets loading 4 words each (76 words = 304 bytes of immediate loads and jumps). The resulting code instructions exceeded the original table (+48 bytes net penalty).
- *Rule:* Only decompose tables when the accessor can return scalar pointers (1 word) or compact discriminants, avoiding multi-register return overhead.

### Fallacy 4: The C-ABI Fixed Overhead Floor
- **The Myth:** "We can trim 5,500 bytes from `runtime::syscall` by making handlers thinner."
- **The Empirical Reality:** `firmware::runtime::syscall` exports 183 separate `extern "C"` functions. On ARMv6-M, an `extern "C"` function that merely forwards arguments has a physical floor of 16 to 24 bytes (prologue, forwarding, call, epilogue).
- $183 \times 16 \text{ bytes} = 2,928 \text{ bytes}$ of irreducible entry/exit glue.
- Individual function thinning yields diminishing returns. Real savings require **reducing the symbol count** through consolidated dispatchers (e.g. single opcode TVF or vector dispatch).

### Fallacy 5: Stream Cursor Abstraction Tax
- **The Myth:** "A structured `WireBuf` writer with helper methods is more idiomatic and smaller than raw slice copies."
- **The Empirical Reality:** Constant-range slice writes (`out[0..2].copy_from_slice(&val.to_le_bytes())`) are optimized by LLVM directly into 1-cycle `strh`/`str` instructions with **zero runtime bounds checks**. A dynamic cursor introduces offset state tracking, mutable pointer register maintenance, and runtime length comparisons (+392 bytes penalty).

## 4. Next-Generation KRX Structured ABI (v3.1) Architecture

### 4.1 Comparative Architectural Autopsy: Why Falcon & F4HWN Fail

Reference firmwares (e.g. Falcon UV-K1/K5v3 and F4HWN OpenApps) pioneered installable applications on amateur radios, but their underlying execution models suffer from structural flaws that compromise silicon safety and real-time determinism:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       EXECUTION MODEL ARCHITECTURAL COMPARISON              │
├────────────────────────────────┬────────────────────────────────────────────┤
│ FALCON / F4HWN FLUID RUNTIME   │ KERN HIGH-ASSURANCE KRX RUNTIME            │
├────────────────────────────────┼────────────────────────────────────────────┤
│ • Untyped C Function Pointers  │ • Strongly-Typed AAPCS-Thumb System Tables │
│ • Zero Capability Gating       │ • Strict Bitwise Hardware Token Checks     │
│ • Raw Register Access Permitted│ • High-Level Microkernel Trait Contracts   │
│ • Blocking `while(1)` App Loop │ • Cooperative Event-Driven Slices (<500 µs)│
│ • No Demand Paging (Fixed RAM) │ • Fixed-Window LRU Paged Overlays & Leaves │
│ • App Crash = Radio Brick      │ • Hardware Quiescence & Safe-Mode Recovery │
└────────────────────────────────┴────────────────────────────────────────────┘
```

#### Flaw 1: Untyped Flat Function Pointer Tables (`void* api_table[]`)
In Falcon/F4HWN, the app API is an unorganized flat array of pointers without domain separation. An application wanting to draw a string receives the same API pointer table as an application configuring the radio's RF power amplifier. If a firmware build inserts a single function pointer in the middle of `api_table`, every precompiled binary in existence suffers a silent offset shift, causing calls to `draw_text` to execute `radio_transmit` instead.

#### Flaw 2: Zero Capability Gating & Hardware Safety Hazards
Falcon/F4HWN applications are granted unmediated access to peripheral silicon registers. An app can write directly to BK4829 register `0x30` or py32 GPIO registers, bypassing safety limits. A bug in userland can lock the RF transmitter in transmit mode, burning out the PA stage or violating FCC/ITU amateur radio transmission regulations.

#### Flaw 3: Blocking Super-Loop Hijacking
Falcon applications run in a blocking `while(1)` loop. While an app is running, the host firmware cannot execute background tasks. Squelch hysteresis, sub-audible tone decoding (CTCSS/DCS), VOX audio analysis, battery voltage monitoring, and RigWire USB RPC are completely halted unless the app explicitly calls a yield function.

#### Flaw 4: Irreducible Monolithic C-ABI Symbol Floor
Exporting 180+ fine-grained C functions (`api_draw_pixel`, `api_draw_line`, `api_draw_char`, `api_draw_rect`) incurs a minimum 16–24 byte prologue/epilogue floor on Cortex-M0+ per symbol. This wastes over **3.2 KB of Flash** purely on C-ABI entry/exit trampolines.

### 4.2 KRX Structured System ABI (v3.1) Specification

To achieve optimal Flash efficiency while guaranteeing silicon-level safety, Kern establishes the **KRX Structured System ABI (v3.1)**. The subsystems align 1:1 with the 13 canonical microkernel primitives:

```rust
#[repr(C)]
pub struct KrxSysTable {
    pub abi_version: u32,             // KRX_ABI_VERSION_3_1 (0x0003_0100)
    pub table_size: u16,              // sizeof(KrxSysTable) = 64 bytes (2^6)
    pub _reserved: u16,               // Alignment pad
    pub granted_caps: u32,            // Bitwise capability token mask

    // 13 Granular Subsystem APIs (1:1 Microkernel Primitive Mapping)
    pub display: *const DisplayApi,   // 0x0001: 2D Graphics, Canvas & Framebuffer
    pub radio: *const RadioApi,       // 0x0002: RF Modem, Tuning, RSSI & Sweep
    pub audio: *const AudioApi,       // 0x0003: Tone Generation & Mic Sampling
    pub storage: *const StorageApi,   // 0x0004: Filesystem, Assets & Configs
    pub keypad: *const KeypadApi,     // 0x0005: Matrix Scanner, PTT & Side Keys
    pub power: *const PowerApi,       // 0x0006: PMU, Battery ADC & Backlight
    pub serial: *const SerialApi,     // 0x0007: USB CDC & UART Communication
    pub timer: *const TimerApi,       // 0x0008: Hardware Timers, RTC & Delays
    pub ui: *const UiApi,             // 0x0009: Modal Dialogs, Toast & Status Bar
    pub math: *const MathApi,         // 0x000A: Hardware CRC32, CRC16 & Fixed-Point
    pub fm: *const FmApi,             // 0x000B: Broadcast FM Tuner (Si4732 / RDA5807)
    pub service: *const ServiceApi,   // 0x000C: Dynamic Linker, IPC & Process Ledger
    pub hw_bus: *const HwBusApi,      // 0x000D: Low-Level I2C/SPI Bus & GPIO
}
```

#### Principle 1: AAPCS-Thumb Register Linkage ($O(1)$ Zero-Cost Dispatch)
When a KRX app starts, the microkernel invokes its entry point with standard ARM register conventions:
- **`r0`**: Operation code (`SYS_OP_INIT = 0`, `SYS_OP_EVENT = 1`, `SYS_OP_RENDER = 2`, `SYS_OP_EXIT = 3`)
- **`r1`**: Immutable pointer to the flash-resident `&KrxSysTable`
- **`r2`**: Event or payload parameter pointer (e.g. `*const KrxEvent`)
- **`r9`**: Guest Static Base / GOT base register (standard ARM PIC convention)

In ARMv6-M machine code, calling a host service through the system table requires only **two CPU instructions** (2 cycles):
```asm
ldr r3, [r1, #DISPLAY_API_OFFSET]  ; Load DisplayApi table pointer (1 cycle)
ldr r3, [r3, #DRAW_STR_OFFSET]     ; Load function pointer (1 cycle)
blx r3                             ; Branch with link (2 cycles)
```
**Architectural Rationale for Cortex-M0+:**
- **Zero Syscall Trap Penalty:** Unlike traditional OS kernels that use the `SVC` (Supervisor Call) software interrupt, which incurs a 45-cycle penalty on ARMv6-M (16-cycle exception entry, 8-word hardware stack push, handler decode, and 15-cycle exception return), direct table linkage executes in **2 to 4 cycles** with zero context switch overhead.
- **Strict Stack Safety:** Before invoking guest code, the microkernel performs a stack margin check (`stack_margin_bytes() >= 96`). If an app is within 96 bytes of stack exhaustion, the call is rejected with `0xFFFF_FFFF` rather than hardfaulting the CPU.
- **Thumb-1 124-Byte Immediate Offset Invariant:** On ARMv6-M, `ldr rX, [r1, #imm]` encodes an unsigned 5-bit offset scaled by 4, granting a direct reach of $31 \times 4 = 124$ bytes. Because `KrxSysTable` is exactly 64 bytes ($2^6$), every subsystem pointer sits at offset $\le 60$ bytes. Every subsystem is reachable in a single 16-bit opcode with zero register reloading or synthetic address generation.

#### Principle 2: High-Level Trait Contracts (Hardware Safety by Design)
The `RadioApi` table exposes **strictly high-level contracts**:
- `rf_tune(freq_hz, bw, step_hz)`
- `rf_set_modulation(mod_type)`
- `rf_set_tx(active)`
- `rf_get_rssi() -> i16`
- `rf_is_carrier() -> u8`

Userland code **never** touches silicon registers. If an application lacks `Cap::RadioTx`, the microkernel's internal arbitrator rejects `request_tx` with `Err(CapError::PermissionDenied)`. Transmission timeouts (TOT), PA thermal throttling, and frequency band limits are enforced by the microkernel's resident state machine, preventing hardware damage.

### 4.3 Storage Permissions & Anti-Brick Protection

Storage in Kern is **not arbitrarily locked to a single sandboxed folder**. System applications (such as File Explorers, Package Managers, Channel/Zone Importers, Hex Editors, and RigWire Serial Bridges) legitimately require access to operational data across the filesystem:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                 CAPABILITY-BASED FILESYSTEM ACCESS PERMISSIONS              │
├─────────────────────┬───────────────────────────────────────────────────────┤
│ CAPABILITY TOKEN    │ PERMITTED OPERATIONS & PATHS                          │
├─────────────────────┼───────────────────────────────────────────────────────┤
│ `Cap::StorageRead`  │ Read any operational file across `/user/`, `/pref/`   │
│ `Cap::StorageWrite` │ Read & write operational data (`/user/*`, `/pref/*`)  │
│ `Cap::StorageAdmin` │ Full filesystem management (mkdir, rename, unlink,    │
│                     │ format partition, install packages to `/user/apps/`) │
│ `Cap::FactoryCalib` │ Exclusive write access to `/sys/calib.*` (Protected)  │
└─────────────────────┴───────────────────────────────────────────────────────┘
```

#### The Three Invariant Anti-Brick Locks (Silicon-Level Protection):
1. **Hardware Calibration Lock (`/sys/calib.dat` & `/sys/calib.sig`):**
   - Contains factory crystal frequency trim, VCO tuning curves, and TX power tables.
   - Guarded at the VFS driver level. Even if an application holds `Cap::StorageAdmin`, writes to `/sys/calib.*` are strictly blocked unless the process holds `Cap::FactoryCalib`. This capability requires either a cryptographic hardware MAC assertion or an explicit physical key sequence held during cold boot.
2. **Physical Memory Decoupling (MCU Flash vs. External SPI Flash):**
   - The PY32F071xB microcontroller internal Flash (`0x0800_0000..0x0802_0000`) hosts the Bootloader, Safe-Mode Recovery, and Microkernel ROM.
   - The filesystem driver communicates exclusively with the external SPI NOR flash chip (`Py25q16`). It is physically impossible for any filesystem call to overwrite, erase, or corrupt internal MCU program memory.
3. **ROM-Resident Safe Mode Recovery Parachute:**
   - Safe Mode Recovery is baked into MCU ROM. Even if a buggy or malicious File Explorer formats the entire external SPI flash, the radio boots in safe mode, recovers, and awaits factory reflashing via RigWire USB CDC.

### 4.4 Sub-Millisecond Determinism Architecture & Concurrency Simulation

An amateur radio is a hard real-time appliance. While applications and services execute, the radio must simultaneously decode sub-audible tones, eliminate squelch tail crashes, service USB CDC RigWire packets, and monitor battery voltage.

#### Real-Time Simulated Scenarios

##### Scenario 1: Foreground Spectrum Waterfall + Carrier Drop (Squelch Tail Elimination)
- **Context:** The user is running a 128x64 Spectrum Waterfall scanning 50 channels. A signal appears on the priority channel; squelch opens; audio PA un-mutes. The remote transmitter releases PTT, sending a 55 Hz reverse burst for 150 ms, followed by immediate carrier loss.
- **Hard Real-Time Constraint:** Audio PA must be muted within **$\le 5\ \text{ms}$** to prevent an abrasive white-noise squelch crash in the speaker.
- **Architectural Solution:**
  - **Tier 0 (Hardware Interrupt / SysTick 1ms):** The BK4829 interrupt or 1ms SysTick ISR samples squelch carrier flags and CTCSS phase reversal in $< 5\ \mu\text{s}$, completely preempting the foreground waterfall drawing calculation.
  - **Tier 1 (Squelch Tail State Machine):** Executes `bsp::pins::AUDIO_PA.set_low()` in **$< 10\ \mu\text{s}$**. The audio amplifier is silenced instantly, with zero squelch crash, even if the userland app is in the middle of a complex math loop.

##### Scenario 2: Foreground UI + Background APRS Packet Decoder + RigWire Serial RPC
- **Context:** User is browsing Settings. In the background, an APRS daemon is decoding 1200 baud Bell 202 audio samples via the Goertzel algorithm, while a connected host PC streams RigWire CAT commands at 115200 baud.
- **Real-Time Constraint:** Serial bytes arriving every 86 µs must not overflow the RX buffer; APRS tone sampling must remain phase-locked; UI navigation must feel instantaneous (<30 ms response).
- **Architectural Solution:**
  - **DMA Ring Buffer:** USART1 hardware DMA streams serial bytes directly into SRAM with zero CPU load.
  - **Run-to-Completion Slices:** The APRS daemon does not run a blocking loop. Instead, it subscribes to `Topic::AUDIO` and executes in bounded **$\le 250\ \mu\text{s}$ slices** per block of 32 samples.
  - **Total Loop Turnaround:** Keypad poll (12 µs) + APRS slice (250 µs) + RigWire packet dispatch (120 µs) + UI tick (150 µs) = **$< 600\ \mu\text{s}$ total loop time**. Sub-millisecond determinism is mathematically guaranteed.

##### Scenario 3: Demand-Paged Overlay Miss during Dual-Watch Scan
- **Context:** A paged KRX overlay (`Class 1`) experiences a cache miss while the radio is running Dual Watch (switching between VFO A and VFO B every 250 ms).
- **Architectural Solution:**
  - LittleFS streams the 1,024-byte overlay block from SPI Flash via SPI DMA in **420 µs**.
  - Because SPI DMA runs asynchronously with CPU interrupts enabled, the 1ms SysTick ISR and radio priority timer fire normally during flash transfer. Dual Watch cadence is maintained with zero jitter.

#### Concurrency Model: Single-Stack Shared Execution Arena
On Cortex-M0+ with 16 KB SRAM, allocating dedicated 1 KB thread stacks for 8 processes would consume 8 KB (50% of the entire chip's RAM!).
Kern eliminates stack bloat by using the **Single-Stack Run-to-Completion Architecture**:
- All processes, services, and daemons share the main system stack (`MSP`).
- Each event slice (`on_event`, `tick`) runs to completion and unwinds its stack frame before the next process runs.
- Transient state for the active foreground app resides in the 4 KiB `TRANSIENT_ARENA`.
- Background daemons maintain compact static state structs (64–256 bytes in the process table).
- Result: **Up to 8 concurrent processes execute simultaneously using less than 2 KB of SRAM total!**

### 4.5 Near-Silicon Native Execution Speed & Dispatch Optimization

To achieve execution latency as close to bare silicon as possible while maintaining safety guards:

#### 1. Split-Phase Preflight Validation
- **Load-Time Static Verification (`load_native_from_storage`):**
  - Full memory layout execution permissions check (`mem_layout.validate_access`) runs once at package load time.
  - GOT base register (`got_base`) 4-byte alignment and arena bounds validation runs once at package load time.
- **Hot-Path Fast Guards (`invoke_krx_native`):**
  - Eliminated the per-event and per-frame `MemoryRegionDescriptor` iteration loop that previously called `__aeabi_uread4` software helpers.
  - Eliminated the 44-byte stack allocation in `invoke_krx_native` (code size dropped from 240 bytes to 84 bytes).
  - Retained essential silicon guards: 1-cycle Thumb-1 mode bit check (`tst r0, #1`), 2-instruction arena bounds compare, and lightweight Cortex-M0+ stack margin guard (`MSP` vs `_stack_end`).
  - Total dispatch overhead before `blx r6`: **~20 clock cycles (< 0.4 µs @ 48 MHz)**.

#### 2. Call Stack Flattening & Inlining
- Marked `invoke_guest` and `invoke_guest_event` with `#[inline(always)]`, eliminating nested call frames and register spills during 20–50 Hz rendering and rapid key event loops.
- Eliminated redundant `apply_slot_status_bar` pre-call in `native_on_render`, halving status bar string slicing and icon iteration work per frame.
- Replaced intermediate `Option<KrxEvent>` matching in `native_on_event` with direct stack construction and early returns.

#### 3. Power-of-Two Arithmetic on Cortex-M0+
- In `FixedWindowCache::slot_byte_offset`, replaced dynamic integer multiplication with exact bit-shift instructions (`slot_idx << 9` for 512B pages, `slot_idx << 10` for 1024B pages), avoiding the Cortex-M0+ multi-cycle multiplication sequence.

## 5. Declarative Dynamic Settings with Icons (`PrefModule` 2.0)

### 5.1 The Resident Menu Bloat Problem
Currently, `SettingsApp` occupies **7,460 bytes of Flash**, largely because it hardcodes menu structures, navigation trees, and option strings for 18 distinct pages.

### 5.2 The `PrefModule` Declarative Architecture
Instead of compiling dedicated submenus into the firmware for every peripheral, digital mode, or application, the microkernel introduces **Declarative `PrefModule` Descriptors**:

```rust
#[repr(C, packed)]
pub struct DeclSettingItem {
    pub title: [u8; 12],   // Null-padded display name (e.g. "Beacon Rate\0")
    pub icon_id: u8,       // Standard 8x8 icon token (ICON_RADIO, ICON_BATTERY, etc.)
    pub kind: u8,          // TOGGLE (0), CHOICE (1), RANGE (2), ACTION (3)
    pub val_offset: u8,    // Byte offset into app's config file (/pref/app_<id>.cfg)
    pub min_val: u8,       // Minimum range or choice count
    pub max_val: u8,       // Maximum range or choice mask
    pub aux: u16,          // Option string offset or action ID
}
```

#### How It Works at Runtime:
1. **Core Resident Settings (Zero Bloat):** The resident firmware contains only essential system settings: `Display`, `Audio`, `Keys`, `Battery`, `System`.
2. **Dynamic Service Integration:** When an app, daemon, or service registers with the `ServiceRegistry` (e.g. APRS Daemon, Satellite Pass Tracker), it exports a `PrefModule` descriptor slice.
3. **Automated GUI Generation:** When the user enters Settings, the resident engine scans active modules and dynamically renders the menu using shared, lightweight rendering routines with 8x8 bitmap icons.
4. **Zero-Code Extensibility:** Adding a new digital mode with 10 configurable parameters costs **0 bytes of resident firmware Flash**.

## 6. Ultra-Lean Hardware-Safe Panic Subsystem

### 6.1 Contrast with Other Amateur Radio Firmwares
| Firmware | Behavior on Hard Fault / Panic | Recovery Mechanism |
|---|---|---|
| **Stock Quansheng** | Silent freeze or infinite loop; speaker may emit continuous loud buzz | Power cycle via physical volume knob |
| **OpenRTX / DeltaFW** | Minimal text or immediate CPU reset; no forensic data preserved | Re-flash firmware if boot-loop occurs |
| **Kern Microkernel** | **Multi-stage Hardware Quiescence + Non-Volatile Tombstone + 10s Auto-Reset** | **Resident Safe Mode Parachute** |

### 6.2 The Four Invariant Stages of Kern Panic Execution
1. **Stage 0: Hardware Quiescence Gate (`enter_hardware_safety_gate`):**
   - Audio PA pulled LOW immediately (eliminates speaker screeching and pop damage).
   - Flashlight pulled LOW; RF transmitter forced into standby.
   - Status LED switched to solid RED; Watchdog re-armed.
2. **Stage 1: Invariant Forensics Extraction:**
   - Stack frame unpacked directly without tuple spilling.
   - Registers `PC`, `LR`, `SP`, `xPSR`, and caller stack words dumped into the packed `BootSlot`.
   - Fault cause categorized (`STACK_OVF`, `INVSTATE`, `IBUSERR`, `UNALIGNED`, `DACCVIOL`).
   - Crash signature CRC32 calculated and committed to persistent RAM/Flash.
3. **Stage 2: Ultra-Lean Direct Rasterization:**
   - LCD controller initialized directly via SPI without OS scheduler dependencies.
   - Contrast set to EV 31 (optimal 50%); display powered on.
   - Direct font rendering of inverted header (`PANIC! #01`), 5-row register matrix (`PC`, `LR`, `SP`, `ACT`, `RSN`, `STK`, `CRC`), and direct key legend (`[M] Reset`, `[EXIT] Reboot`).
   - Zero widget overhead, zero heap allocation, zero string formatting libraries.
4. **Stage 3: Auto-Reboot Countdown & Watchdog Safeguard:**
   - 10-second countdown runs in a tight delay loop, refreshing the header.
   - If unattended, the radio resets automatically, preventing overnight battery drain with the backlight on.
   - Pressing `[M]` or `[EXIT]` triggers immediate `cortex_m::peripheral::SCB::sys_reset()`.
